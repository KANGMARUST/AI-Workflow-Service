# 견적 아카이브 AI - 개발 명세 (범위 정정)

### 개인 API 키 포함 여부 점검 (2026-10-14, 완료)

사용자는 개인 API 키가 현재 들어 있지 않은지 확인하고, 향후 사용자가 자신의 API 키를 입력하도록 할 의도를 재확인했다. 현재 구현은 웹 사용자 입력 키를 현재 탭 메모리와 해당 분석 요청에서만 사용하는 구조다. 실제 Chrome의 API 설정 화면에서 키 입력값 없음·API 미적용·로컬 분석 상태를 값 노출 없이 확인했다.

개인 키 파일의 Upstage 키를 메모리에서만 대조하여 프로젝트 소스·설정·프론트 빌드 결과·DB·백업·로그 등 85개 파일에 동일 키가 없는지 확인했다. 키 형태 검사도 검출 0건, 읽기 오류 0건이다. 실제 DB와 백업 4개를 포함했다. 환경설정 파일은 .env.example 2개이며 키 변수 값이 없고, 점검 명령 프로세스의 UPSTAGE_API_KEY/OPENAI_API_KEY도 미설정이다. 프론트 기본 키는 빈값이며 App.jsx의 브라우저 저장소 참조가 없고 서버 user_agent.py는 요청 헤더에서만 인증 키를 받는다. tests/live_quote_agents.py의 개인 키 읽기는 개발 테스트 전용이다.

결과는 tests/api-key-presence-results.json에 키 값 없이 기록했다. 원본 견적 파일·의존성 패키지·OCR 모델, 외부 Studio의 발급 키 목록은 검사 범위에서 제외했다. 실행 중인 서버 프로세스 환경은 직접 읽지 않았으며 현재 서버 코드에 환경 키 사용 경로가 없음을 확인했다. 실 API 호출·키 삭제·코드 변경은 하지 않았다. API 요청 분리는 기존 구현이며 로그인·사용자별 문서 접근 권한 구현을 의미하지 않는다.

### 프로젝트 외 Studio 에이전트 삭제 (2026-10-14, 완료)

사용자 요청과 영구 삭제 최종 확인에 따라 Studio의 장사비서_Diagnosis_Prototype·Operations_Prototype·Sales_Prototype, Resume Agent, 강희찬_미션1_JD Agent 총 5개를 삭제했다. 삭제 완료 후 웹 목록에서 견적아카이브_추출·검토·비교 3개만 남아 있고 프로젝트 Agent ID와 일치하는지 확인했다. 파일 7개 추가 삭제 옵션은 선택하지 않았다. 대상 ID·확인 과정·한계는 docs/AGENT_WORKFLOW.md, 최종 화면은 tests/qa/studio-agents-after-delete.jpg에 기록했다. 로컬 원본·DB·연결 코드는 변경하지 않았으며 빌드·실 API 호출은 필요하지 않아 실행하지 않았다.

### 에이전트별 API 입력 안내 (2026-10-14, 완료)

요청: Studio 에이전트가 여러 개라 어떤 정보를 입력해야 하는지 혼동하므로 웹에 설명을 추가한다. API 설정에는 PDF 등록용 견적아카이브_추출 Agent ID를 입력한다고 명시하고, 작업실에는 선택한 추출·검토·비교 역할의 실제 Studio 이름과 사용 목적을 표시한다. 계정 인증용 Upstage API Key, 실행 대상 Agent ID, 설정 버전 Config ID를 구별해 안내한다. 기존 생성 계정의 3개 ID·Config ID 1을 표로 제공하고 다른 계정은 접근 가능한 자신의 역할별 ID·버전을 입력하도록 설명한다. 검증은 frontend build와 실제 브라우저의 API 설정·작업 전환·좁은 화면 확인이며 실 API 호출은 필요하지 않다.

구현: frontend/src/AgentConnectionGuide.jsx에 역할별 이름·설명·입력 위치·ID 표와 API Key/Agent ID/Config ID 설명을 추가했다. App.jsx의 입력란을 PDF 등록용 추출 Agent ID·추출 설정 버전으로 표시하고, AgentWorkspace.jsx는 선택한 역할의 Studio 이름·용도와 전체 안내 이동 버튼을 표시한다. 역할별 ID 상수는 공유한다. README와 docs/AGENT_WORKFLOW.md의 사용 안내도 갱신했다.

검증: 최종 frontend production build 성공. 연결된 Chrome의 실제 로컬 앱에서 API 안내 표·입력란 한글·추출/검토/비교 역할 전환과 각 ID 일치를 확인했다. 390×844 화면에서 설명 줄바꿈과 표 스크롤 안내를 확인했으며 페이지 너비 375px, 표 영역 255px 안에서 760px 표를 스크롤하는 구조다. 임시 화면 크기는 복원했다. 초기 편집 과정의 한글 인코딩 오류는 수정 후 화면에서 재확인했고, 최초 빌드의 실행 폴더 오류(프로젝트 루트 package.json 없음)는 frontend에서 실행하여 해결했다. 증거: tests/qa/agent-api-guide.jpg, agent-role-guide.jpg, agent-api-guide-mobile.jpg; 결과: tests/agent-api-guide-results.json.

범위·한계: 이번 변경은 연결 설명과 입력란 표시다. 실 API 호출과 권한 확인은 수행하지 않았고 기존 원본·DB·Studio 설정은 변경하지 않았다. 다른 계정은 본인의 역할별 ID와 버전을 입력해야 하며 작업실에서 작업을 전환하면 표시된 ID·버전을 다시 확인해야 한다.

## 1. 사용자의 확정 의도
사용자는 “새 견적서 만드는 거 아닌데”라고 정정했다. 목적은 이미 발행된 견적서에서 정보를 추출하여 검색 가능한 데이터베이스로 정리하고 조회하는 것이다. 최신 개요/목표/주요 기능이 기준이며 하단에 남은 과거 작성/초안/출력 문구는 현재 요구사항으로 적용하지 않는다.

**기존 파일 업로드 → 정보 추출 → 원본 대조·오류 정정 → 저장 → 거래처/담당자/제목/품목/기간 검색 → 결과 목록 → 상세·원본 조회.**

새 견적 작성, 빈 견적 생성, 복사, 수량 변경으로 가격 산정, 양식 관리, 새 견적 Excel/PDF 출력은 제거한다. 수주/미수주 영업 흐름도 중심 화면에서 제거한다. 수정은 추출 오류의 정정이며 원본 파일은 변경하지 않는다.

## 2. 자료와 보존 원칙
project/data에 사용자 Input_data의 PDF 2개와 XLS 1개를 로컬 참조한다. 원본과 기존 DB는 삭제하지 않는다. 과거 복사 시연 견적은 아카이브에서 제외하고 DB에는 보존한다.
- 첫 PDF: 공급가액 16,000,000원, VAT 별도, 3품목. 없는 세율/세액/세금포함총액을 임의 생성하지 않는다.
- 복합 PDF: 공급가액 266,740,000원, 5패키지+15부품. 패키지/부품 관계를 보존하며 중복 합산하지 않는다.
- XLS: 3품목 중 2·3번은 대체 옵션이고 합계는 “선택”이다. 모든 옵션을 검색·조회 대상으로 보존하고 선택을 강제하거나 임의 합계를 만들지 않는다. 합계미기재와 선택 조건 표시.
- PDF의 시각 익명화와 내부 텍스트가 다를 수 있다. 숨김 연락처는 마스킹, 원본 화면 확인 후 연락처/담당자 보완 가능.

## 3. 화면/결과물
- 기본 진입: 견적 보관함. 파일 등록과 검색·필터를 중심에 배치.
- 검색: 거래처, 담당자, 연락처, 제목/프로젝트명, 품목/규격, 원본 견적번호, 기간, 원본 금액, 검토 상태.
- 목록: 제목/견적번호, 거래처, 담당자, 작성일, 품목수, 원본 금액·VAT 기준, 검토 상태, 원본 접근.
- 상세: 원본과 추출 원문, 헤더, 모든 품목/사양/옵션·부품구분, 경고, 추출 오류 정정·검토 완료, 정정 이력.
- 원본 수량/단가/금액을 수정하더라도 다른 값을 자동 계산해서 덮어쓰지 않는다.
- 품목 이력/단가 조회: 모든 원본 품목(옵션·부품 포함), 거래처/담당자/일자/규격/단위/통화/수량/원본단가/조건을 표시.
- 현황: 등록 문서수, 검토 필요, 거래처수, 저장 품목수. 새견적/수주실적 중심 UI 제외.
- 자연어 검색: 저장된 견적의 담당자·제목·품목·날짜 조건을 해석하는 보조 기능.

## 4. 데이터 및 검증
Quote: id(시스템 ID), number(원본 견적번호, 없으면 빈값), customer, issuer, contact(발행 담당자), customer_contact(고객 참조 담당자), phone, email, project_name(제목), issue_date, valid_until, delivery, ship_to, payment_terms, currency, tax_note(원본 VAT 조건), subtotal/total/tax/tax_rate(원본 명시값만), source_total/source_total_kind, source_name/source_url/source_text, review_status, version, created_at/updated_at, warnings, items, original_fields(원본 추출 기준값).
Item: name, specification, unit, quantity, unit_price, amount, original_text, is_component, parent_index, option_group. 선택옵션은 모두 보존하며 included로 숨기거나 선택하지 않는다.

원본 값을 보존한다. 계산 검사는 별도 computed_amount/computed_subtotal에만 기록한다. 원본 amount/subtotal/total을 계산값으로 대체하지 않는다. VAT 별도이고 세율이 없으면 tax_rate/tax/total은 null, 공급가액과 VAT별도 기준을 표시한다. 합계 미기재는 null·사유 표시.
누락·불일치는 원본 대조 경고다. 원본 자체가 불명확하면 담당자 확인 후 저장 가능하며 옵션 미선택은 차단하지 않는다. 식별용 거래처/품목 정보는 검토 중 보완한다.
기존 추정10%/생성금액은 원본 자료를 다시 확인하여 바로잡되 원본 파일은 변경하지 않는다. 기존 원본없는 생성/복사 자료는 아카이브 목록/검색/통계에서 제외한다.

## 5. API
유지: GET health, GET quotes(명시적 contact/phone/title 필터), GET quotes/{id}, POST upload/import-samples, PUT quotes/{id}(오류 정정), POST confirm(검토 완료), GET history, GET files, GET compare(원본 모든 품목), POST natural-search, GET stats(아카이브 현황).
비활성: POST quotes, copy, status 변경, templates CRUD, quote export → 404/410. 새견적 생성 API로 우회할 수 없다.
구조: project/frontend(React/Vite), backend(FastAPI/SQLite·선택PG), data, tests. 프론트/백/검증 에이전트는 이 MD를 먼저 읽고 담당 폴더만 수정한다.
